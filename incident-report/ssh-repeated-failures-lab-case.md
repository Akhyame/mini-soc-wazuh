# SOC case MINI-SOC-2026-09-23-SSH-01 — Repeated SSH failures

**Disposition:** Closed as a **benign, authorized lab test**. This report is not a claim of a real security incident, intrusion or compromised account. This self-contained public report includes the findings, timeline, disposition and links to the [public source-log evidence index](../docs/evidence-index.md). No private notebook access is required.

## Executive summary and scope

On **23 September 2026**, controlled incorrect SSH passwords to the monitored Ubuntu VM's **own loopback interface** produced source journal events and a Wazuh alert for custom rule **100100**, configured at **level 10**, for repeated failed authentication from one source. The tested account was the lab account `agentadmin`, the source and target were `127.0.0.1` on `mini-soc-agent`, and the isolated VMware Host-only lab was under the operator's control. Level 10 is a **configured alert level**, not an independently assessed impact rating.

The central Wazuh 4.14.7 server collected `journald` events from `mini-soc-agent` and displayed the matching event under Threat Hunting. No outside address or third-party system was targeted.

## Analyst interpretation and response

**Established:** A bounded, same-source repeated SSH failure pattern was recorded on the Ubuntu endpoint; Wazuh indexed a matching custom-rule alert. These events were deliberately generated by the lab operator. The loopback source IP does **not** indicate an external attacker. Neither a successful compromise nor unauthorized privilege escalation was demonstrated.

**Possible benign alternative in other environments:** An authorized user repeatedly entering a wrong password can produce similar alerts; shared source-IP scenarios can also mislead grouping by IP.

**Disposition and lab handling:** Classify this alert as *authorized test / benign activity* after confirming the planned exercise. No host isolation, source-IP block, forced password reset or account lockout follows from the facts of this controlled test. For an **unexpected** real-world alert, establish whether the activity was authorized, inspect the affected account/source and adjacent successful logins, review endpoint/network context, and decide containment on the broader verified evidence rather than the failed-password pattern alone.
